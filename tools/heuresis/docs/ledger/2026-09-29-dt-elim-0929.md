# 2026-09-29 — `dtElim-0929`, with and without conflict-based instantiation

**Goal 3, a new R16 proposal.** A fresh implementation of datatype elimination,
[`ajreynol:dtElim-0929`](https://github.com/ajreynol/cvc5/tree/dtElim-0929),
run with the reference prefix and also with `--no-cbqi` removed. Each arm has a
reference at the branch's own base. **Complete**: 4 runs, one each.

## 1. What was asked

Add and test the branch. It declares `--dt-elim` [`false`], an expert option
that inlines single-constructor datatypes in preprocessing. Its help text says
it has no model generation and that unsupported type contexts raise logic
exceptions. It is not a descendant of the earlier
[`dtElim`](2026-09-24-branch-sweep.md) branch, whose `--dt-elim` measured −945.
The maintainer also asked for a run without `--no-cbqi`.

## 2. What was run

The branch is one commit,
[`0731894e97`](https://github.com/ajreynol/cvc5/commit/0731894e973d65dc0f543c688dfea107b5cb9ec7)
("Another attempt at dt elim"), on
[`4692619e6a`](https://github.com/cvc5/cvc5/commit/4692619e6a2ee8d4faff9fab735f84c809a616fe).
That base is on upstream cvc5 `main`. The one fork-`master` commit the branch
lacks is a CMake-only fix. The diff is +703/−0 over 9 `src/` files, mostly
`preprocessing/passes/dt_elim.cpp`, plus a 246-line unit test.

Everything was built in the branch-sweep build directory, with the same checks
as the [2026-09-28 sweep](2026-09-28-ai-heuresis-branch-sweep.md): each build's
`--show-config` hash was verified, and each arm's options were smoke-tested
before the run. The builds took 41–66 s. The runs were driven by scripts on the
host, so there is no `job_launcher/log.txt` entry. Each ran `solve_dir_rec_par_cvc5
-t 30 <binary> cvc5_solve.sh quant-092926-<w4|w4b>-<arm> <options>`.

| run | commit | options |
| --- | --- | --- |
| `w4-reference` | `4692619e6a` | `-q --no-cbqi --user-pat=strict --sat-solver=cadical` |
| `w4-dtelim-0929` | `0731894e97` | the same + `--dt-elim` |
| `w4b-reference-cbqi` | `4692619e6a` | `-q --user-pat=strict --sat-solver=cadical --cbqi` |
| `w4b-dtelim-0929-cbqi` | `0731894e97` | the same + `--dt-elim` |

## 3. The set

`quant-07-25`, 6124 benchmarks, 30 s, one arm at a time on the idle host.

## 4. What came back

Results are `results-cvc5_solve.sh-quant-092926-<run>.txt` on the host, read
with the [`gap`](../../reports/gap) parser as in the 2026-09-28 entry.

**The reference at `4692619e6a` solves 5577**, 5 unknown, 542 timeout, PAR2
39324.6. Against the 5576 run at `d7d5b948c1` in the same directory it is
**+5 / −4**, inside noise. The QCF-on control solves 5563, which is +2 / −16
against it. That matches the −14 `--cbqi` measured at `d7d5b948c1`.

| arm | against | gained | lost | net | crashes | timeout | PAR2 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `--dt-elim` | the reference (5577) | +0 | −2090 | **−2090** | 480 | 2157 | 161427.6 |
| `--cbqi --dt-elim` | the QCF-on control (5563) | +0 | −1888 | **−1888** | 421 | 2028 | 151135.0 |
| `--cbqi --dt-elim` | the reference (5577) | +0 | −1902 | **−1902** | 421 | 2028 | 151135.0 |

**No arm gains a single benchmark, and none disagrees with its reference on sat
versus unsat.** The two arms took 1267 s and 1316 s, against about 430 s for a
normal run.

**The crashes.** 480 and 421 benchmarks return no output at all, which the
wrapper records as the token `none`. Re-running one,
`sundance/UFDTLIA/20241211-verus/atmosphere/process_manager__container_tree_spec_impl.14.smt2`,
exits with status 139, a segfault. Almost all are in the datatype families: 352
`UFDTLIA` and 109 `UFDTNIA` in the first arm. **The wrapper does not log a
reason for this case.** It prints `none` whenever cvc5's output is empty and
returns before `log_reason`, so both error logs are empty although every `none`
is a crash. `gap` counts `none` as unsolved, so the numbers above are right.

**The timeouts are not slowness at the margin.** Of the benchmarks the first arm
loses to timeouts, 1104 are ones the reference solves in under a second.
Re-running two confirms it: `mathmain!math.lemma_mul_ordering._01` takes 0.03 s
without `--dt-elim` and still runs at 30 s with it. For 5 s of that run, the
`dt-elim` pass itself takes 3 ms; the time goes to search, with 4977 ms in the
SAT solver and 883531 rewrite steps.

## 5. What it settled

**`dtElim-0929` is red with either quantifier setting and cannot be
proposed.** It loses a third of the set, rescues nothing, and crashes on over
400 benchmarks. Conflict-based instantiation does not change that: the QCF-on arm
loses 1888 against its own control. This is worse than the first `dtElim`, which
lost 954 and gave up with `unknown` rather than crashing or hanging. R16's
evidence against eliminating datatypes wholesale is now two independent
implementations.

## 6. What it did not settle

**Why the search collapses.** The pass is fast and the problems it produces are
far harder. One hypothesis, untested, is that inlining changes the terms the
strict user patterns refer to, so E-matching loses its triggers. The crash has
no backtrace yet. Whether the two failures share a cause is unknown.
