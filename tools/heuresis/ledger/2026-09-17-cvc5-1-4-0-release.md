# 2026-09-17 — the cvc5 1.4.0 release, measured

**Measuring stick.** Both tracked configurations at the 1.4.0 release point,
to see whether the release moved anything on this set.

## 1. What was asked

`ajreynol:master` reached the cvc5 1.4.0 release. [`progress.md`](../docs/progress.md)
exists to answer exactly this: did a release of cvc5 change what these
benchmarks cost?

## 2. What was run

The binary was `master@a07d513075`, which reports
`cvc5 1.4.1.dev+master@a07d513075`. **It is one commit past the release**: the
`cvc5-1.4.0` tag is `b432cd77eb`, and the two differ only in
`cmake/version-base.cmake`, with **no changes under `src/`**. Measuring master
therefore measures the release.

Before the runs, the diff against the previously measured revision was read:

```
a07d513075  Start post-release for 1.4.0    <- measured here
b432cd77eb  Bump version to 1.4.0           <- tag cvc5-1.4.0
67954d09dc  Build wasm with CoCoA (#12849)  <- previously measured
```

`git diff 67954d09dc a07d513075` is **one line, in `cmake/version-base.cmake`**.
So this run was expected to reproduce the previous row, and was carried out as
confirmation rather than discovery. That expectation is recorded here because
it was formed before the numbers were seen.

```
# quant-091726-u-ssc-140       -q --no-cbqi --user-pat=strict --sat-solver=cadical
# quant-091726-u-ssc-best-140  … --ee-mode=central --ieval=off
```

New job tags were used rather than the existing ones, so that the
`67954d09dc` artifacts needed for the comparison were not overwritten.

## 3. The set

`quant-07-25`, **6124 benchmarks**, 30 s each, both arms reading all 6124. The
reference is the full-Verus-option z3 4.15.4 run of
[`2026-09-15`](2026-09-15-z3-full-verus-options.md), PAR2 23413.7.

## 4. What came back

| config | revision | solved | timeout | PAR2 | ratio | gap | Δ |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| verus | `67954d09dc` | 5548 | 571 | 41142.2 | 1.76 | 1073 | — |
| verus | **`a07d513075`** | 5545 | 574 | **41191.8** | 1.76 | 1079 | **+0.12%** |
| best | `67954d09dc` | 5626 | 471 | 35532.7 | 1.52 | 784 | — |
| best | **`a07d513075`** | 5624 | 473 | **35580.3** | 1.52 | 786 | **+0.13%** |

No `sat` answers, no disagreements, and no `error` results in either arm: at a
30 s timeout neither of the two benchmarks that
[segfault](2026-09-17-central-ieval-segfault.md) reaches the fault.

## 5. What it settled

**The 1.4.0 release changes nothing on this set, and that was predictable from
the diff.** Both configurations move by about a tenth of a percent — three and
two net solves respectively, in the direction of slightly worse — which is
comfortably inside the ±0.2% band. With one line of `cmake` between the two
revisions, any other outcome would have indicted the measurement rather than
cvc5.

**The noise band survives a fifth measurement.** `verus` now spans 0.37% over
five measurements and `best` 0.24%, unchanged from four. The band is not
widening as points accumulate.

**The plateau is now a release-to-release statement.** Every cvc5 revision this
project has measured, from `5cc03f4b9` to the 1.4.0 release, performs the same
on these benchmarks to within noise.

## 6. What it did not settle

This is a null result about a release whose diff was already known to be
empty; it is evidence about the measurement's stability, not about cvc5's
development. It says nothing about the revisions *between* `5cc03f4b9` and
`67954d09dc`, which were never measured individually — a regression that
appeared and was fixed inside that window would be invisible here.

The `best` arm remains the configuration with a known segfault, and the gap
sets (1079 and 786) drift by a handful of benchmarks between identical
configurations, as they have throughout.
